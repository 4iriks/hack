## 2. ДИАГНОСТИКА: Почему потолок на 0.097?

### Гипотеза A: Модель видит правильные паттерны, но данные зашумлены
- Fraud и confirmed ОЧЕНЬ похожи (оба "подозрительные")
- operaton_amt: fraud 23,800 vs confirmed 14,946 — различие есть, но overlap огромный
- Только 412 клиентов имеют И fraud, И confirmed — модель не видит различия на уровне клиента

### Гипотеза B: Агрегаты несовместимы с train sample
- Velocity фичи (cnt_30d, amt_sum_7d) считаются по ПОЛНЫМ 85M строкам
- Но train — это sample 2.6M строк (50:1 ratio green)
- Модель видит cnt_30d=50 для клиента, но в train только 1-2 его строки
- **Это ГЛАВНАЯ проблема v11** — day_stats ещё сильнее обнажили этот конфликт

### Гипотеза C: Недоиспользование временной структуры
- 191M строк = полная история транзакций каждого клиента
- Мы используем только ТОЧЕЧНЫЕ фичи (на момент транзакции)
- НЕ используем: последовательность транзакций, паттерн дня, сравнение с историей
- Фрод-день отличается от обычного дня ПАТТЕРНОМ, а не отдельной транзакцией

### Гипотеза D: Неоптимальная гранулярность предсказания
- Тест = один ДЕНЬ на клиента (все транзакции дня)
- Мы скорим каждую транзакцию отдельно
- Нужно скорить ДЕНЬ клиента как единое целое
- Customer-day boosting работает (+8.7%) именно потому, что движется в эту сторону

## 3. ПЛАН: Три стратегических направления

### 🔴 Направление 1: ПРАВИЛЬНЫЙ TRAIN (быстрый потенциал)
**Суть:** Обучать на ПОЛНЫХ днях, а не на случайных строках.

**Проблема сейчас:**
- Train = 2.6M случайных строк (green sampled 50:1)
- Velocity-фичи (cnt_30d=50) не соответствуют train (1-2 строки клиента)
- Модель учится на искажённой картине

**Решение:**
1. Собрать train по-другому: для каждого labeled клиента взять ВСЕ его транзакции за день с событием
2. Добавить полные дни случайных green-клиентов (negative sampling на уровне дней, не строк)
3. Velocity-фичи будут согласованы: cnt_30d=50 → и в train 50 строк видны
4. Это гармонизирует фичи с реальностью

**Оценка:** Устраняет корневую причину (гипотеза B). Потенциал: +20-50% PR-AUC.

**Реализация:**
```
Шаг 1: Из labels получить (customer_id, date) → дни с событиями
Шаг 2: Из 85M чанков извлечь ВСЕ строки этих дней
Шаг 3: Добавить полные дни random green-клиентов (ratio ~10:1 дней)
Шаг 4: Velocity-фичи уже посчитаны в чанках — всё согласовано
Шаг 5: Train LGBM с proper val (уже есть)
```
**Время:** ~30 мин сборка, ~15 мин обучение.

---

### 🟡 Направление 2: DAY-LEVEL ФИЧИ (средний потенциал)
**Суть:** Добавить фичи, описывающие ВЕСЬ ДЕНЬ клиента, а не отдельную транзакцию.

**Почему это может работать:**
- Тест = один день на клиента
- Фрод-день отличается ПАТТЕРНОМ: необычная сумма за день, необычное количество, новые MCC
- Customer-day boosting (+8.7%) работает именно потому что частично ловит это

**Новые day-level фичи (НЕ из day_stats, а считаем в train):**
```python
# Для каждой (customer_id, date) в train:
day_n_ops_today        # сколько транзакций сегодня
day_total_amt_today    # сумма за сегодня
day_max_amt_today      # максимальная транзакция дня
day_n_unique_mcc_today # разнообразие MCC за день
day_pct_of_30d_amt     # сегодня / среднее за 30 дней
day_is_unusual_count   # cnt_today > 2 * avg_daily_cnt
day_security_flags_sum # сумма security-флагов за день
day_has_manual_entry   # был ли ручной ввод сегодня
```

**ВАЖНО:** Эти фичи считаются из ТОГО ЖЕ train, а не из внешних 85M → нет конфликта масштабов!

**Оценка:** Потенциал +10-30%. Согласуется с интуицией "скорить день, не транзакцию".

---

### 🟢 Направление 3: CUSTOMER-DAY POST-PROCESSING (гарантированный прирост)
**Суть:** Улучшить post-processing, который уже доказал +8.7% на val.

**Текущее:** `score × customer_max` → val 0.039 → 0.042 (+8.7%)

**Расширения:**
```python
# 1. Оптимальный бустинг (подобрать alpha)
final_score = score * (customer_max ** alpha)  # alpha ∈ [0.3, 1.0]

# 2. Customer-day statistics
day_max = max(scores for customer on same day)
day_mean = mean(scores for customer on same day)
final = score * (day_max ** a) * (day_mean ** b)

# 3. Conditional boosting: если max > threshold, буст пропорционален
if customer_max > P99:
    score *= boost_factor
```

**Оценка:** Гарантированные +5-10% от val, уже доказано. На LB: 0.097 × 1.087 ≈ 0.106.

- Train: 51K fraud + 259K hard green + 1020K easy green = 1.33M строк
- Модель учит ТОНКИЕ различия вместо тривиальных

### Шаг 5-6: Customer-Day Boost → ЛУЧШИЙ РЕЗУЛЬТАТ (val=0.062, +58%)
- M4: `score^1.21 × cust_max^4.80 × n_high^0.05 × range^-0.11`
- M1 (безопаснее): `score × cust_max^3.13` = val=0.051 (+31%)
- Customer-level PR-AUC = 0.214 — модель хорошо находит fraud-клиентов
