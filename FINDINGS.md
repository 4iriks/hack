## Ключевые прорывы

### 1. Proper validation (v10) — РАБОТАЕТ
- Имитируем тест: один случайный день на клиента из полных 85M строк
- Val: 523K строк, 430 fraud (0.082%) — реалистичное распределение
- Калибровка: val 0.039 → LB 0.097
- Только от правильного early stopping получили +0.002 на LB (0.095 → 0.097)
- Seed 777 дошёл до 9775/10000 итераций — потолок деревьев мешал

### 2. Что НЕ дало эффекта (и об этом стоит помнить)
- Прошлый val (случайный сплит): val 0.62 и val 0.31 давали одинаковый LB ~0.095
- Больше фич: v2 (66 фич) хуже v1 (41 фич), v11 (129 фич) хуже v10 (91 фич)
- Больше данных (то же качество): v8 (2.6M) ≈ v3f (344K)
- Two-stage: v9 хуже v8, разделение задачи не помогло
- Labeled-only: v5 LB=0.068 (без зелёных модель не работает)
- Target encoding: обрушило модель
- PDF-фичи: 3 из 6 с нулевым importance
- **v11 pretest profiles + day stats + MCC reputation = LB 0.075 (ХУЖЕ 0.097!)**
  - Day stats из полных 85M строк несовместимы с сэмплированным train
  - Pretest и test пересекаются по времени (Jun-Aug 2025) — фичи бесполезны
  - MCC reputation: всего 21 MCC-код — слишком грубо
- **Isolation Forest**: val=0.003 (бесполезен для fraud detection)
- **Power transforms скоров**: PR-AUC = rank-based, монотонные трансформы не меняют ранг
- **XGB + CatBoost ансамбль**: 99% вес у LGBM, другие модели не добавляют

### 3. Что ПОМОГАЕТ (подтверждено)
- **Proper validation** (один день на клиента): v10 LB=0.097 > v8 LB=0.095
- **Customer-day boosting** (score × customer_max): val 0.039 → 0.042 (+8%)
  - Идея: если у клиента есть подозрительная транзакция, ВСЕ его транзакции дня подозрительнее
  - Это единственный пост-процессинг, который улучшил val

## Двухуровневая модель — ЛУЧШИЙ РЕЗУЛЬТАТ (2026-03-15)

### Идея
Customer-level PR-AUC=0.214 (vs 0.039 transaction-level) → модель хорошо находит fraud-клиентов.
Двухуровневый скоринг: усилить транзакции подозрительных клиентов.

### Методы (M1-M5)
- M1: `score × cust_max^a` — простой boost
- M2: `score × cust_max^a × cust_mean^b` — с учётом среднего
- M3: `score^a × cust_max^b × cust_mean^c` — гибкий
- M4: `score^a × cust_max^b × n_high^c × range^d` — с количеством подозрительных + разбросом
- M5: `score^a × cust_max^b × (1-cust_rank)^c` — с рангом клиента

## ADVERSARIAL VALIDATION — КРИТИЧЕСКАЯ НАХОДКА (2026-03-16, ночь)

### AUC = 1.0000 — ПОЛНОЕ РАЗДЕЛЕНИЕ train vs test!
Модель за 2 итерации ИДЕАЛЬНО отличает train от test. Огромный distribution shift.

### Главный виновник: `dormancy_days`
- Train mean = 129, Test mean = 279 (shift = **2.13σ**)
- Adversarial importance = 2,825,063 (98.8% всей importance!)
- **Причина**: dormancy = дни с последней транзакции в customer_profiles
- Профили считаны из train периода → для test клиентов dormancy автоматически больше
- Это **ВРЕМЕННАЯ УТЕЧКА** — фича кодирует "это train или test", а не фрод

### Топ-5 опасных фич (shift × importance)
| # | Фича | Shift (σ) | Adv. Importance | Опасность |
|---|-------|-----------|-----------------|-----------|
| 1 | **dormancy_days** | 2.13 | 2,825,063 | КРИТИЧЕСКАЯ |
| 2 | month | 0.15 | 19,323 | train=Oct-May, test=Jun-Aug |
| 3 | weekday | 0.06 | 11,394 | мелкий shift |
| 4 | session_ops_before | 0.29 | 1,712 | значимый shift |
| 5 | cust_tenure_days | 0.15 | 695 | временная зависимость |

### Перекрытие клиентов
- 100% test клиентов есть в train (94,207 из 94,241)
- Только 34 клиента уникальны для test
- Проблема НЕ в новых клиентах — а в сдвиге фич по времени

### Что это значит для модели
`dormancy_days` — 5я по важности фича в v10 (2.6% gain). Модель ИСПОЛЬЗУЕТ её для предсказания.
Но в test эта фича систематически завышена → предсказания сдвинуты.
Это может быть причиной потолка 0.097 и провала пост-процессинга.

### Adversarial V2: удаление фич не решает проблему!
| Эксперимент | Фич | Adv. AUC |
|------------|------|----------|
| Baseline | 91 | 1.0000 |
| Без dormancy_days | 90 | 1.0000 |
| Без dormancy+month | 89 | 0.9275 |
| Без топ-5 опасных | 86 | 0.8469 |
| Без 11 temporal+session | 81 | 0.8169 |
| Нормализация dormancy+month | 91 | 1.0000 |
| Нормализация 10 фич + без month | 90 | 1.0000 |

**Вывод: shift ПЕРВАCИВНЫЙ.** Нельзя убрать несколькими фичами.
Нормализация (rank) тоже не помогает — shift в совместном распределении, не в маргиналах.

**Вероятная корневая причина:**
- Train = random sample из всего периода (Oct'24-May'25)
- Test = ПОЛНЫЕ дни из более позднего периода (Jun'25+)
- cnt_6h: train=4.1, test=6.3 (полные дни = больше транзакций)
- cnt_24h: train=8.3, test=11.0 (то же)
- Velocity фичи систематически выше в test потому что это полные дни

### План действий (обновлён)
Простое удаление фич не поможет. Нужно:
1. Обучить v10 без опасных фич — проверить, помогает ли хоть немного
2. Сильнее регуляризация (max_depth, lambda, min_child_samples)
3. Temporal sampling: собрать green из ПОСЛЕДНИХ месяцев train (ближе к test)
4. Feature engineering: сделать фичи ИНВАРИАНТНЫМИ ко времени (ratios вместо абсолютных)

## Pipeline v14: Per-Customer Anomaly Detection (2026-03-16, в процессе)

### Идея
Фрод = аномалия для конкретного клиента. Вместо "как выглядит фрод" учим "как выглядит норма Васи".
Если транзакция не похожа на обычное поведение этого человека → подозрительно.

### Почему это может сработать
- **Убивает distribution shift**: мы учим не "паттерны из train-периода", а "норму каждого клиента"
- **Использует ВСЕ 177M строк** (pretrain 91M + train 86M) — ранее использовали только 2.6M (1.4%)
- **100% клиентов общие** между train и test → для каждого есть глубокий профиль
- **Медиана 1700 транзакций на клиента** — достаточно для точного профилирования

### Фаза 1: Deep Customer Profiles (ГОТОВО)
Из 177M строк посчитали для каждого из 100K клиентов (39 колонок):
- **Суммы**: mean, std, median, p10-p99, max, min, IQR, CV
- **Время**: hour mean/std, pct_night, pct_weekend, hour_entropy
- **Мерчанты**: n_unique_mcc, mcc_entropy, top_mcc, + per-customer-MCC amount profiles (1.3M пар)
- **Каналы**: n_unique_channel, n_unique_os
- **Частота**: daily_mean, daily_max, daily_p95, n_active_days, tx_per_day
- **Gaps**: gap_mean, gap_std, gap_median, gap_p95
- **Безопасность**: voip_rate, rdp_rate

Время подсчёта: ~45 секунд (Polars lazy scan).

### Фаза 2: Anomaly Features (18 фич)
Для каждой транзакции — насколько она отличается от нормы ЭТОГО клиента:
- `anom_amt_zscore` — z-score суммы vs история клиента
- `anom_amt_vs_median/p95/p99` — ratio к привычным суммам
- `anom_amt_above_max` — сумма БОЛЬШЕ чем клиент когда-либо тратил
- `anom_amt_iqr_score` — outlier по IQR
- `anom_hour_zscore` — нетипичный час для этого клиента
- `anom_night_unusual` — ночная транзакция для "дневного" клиента
- `anom_weekend_unusual` — выходной для "будничного" клиента
- `anom_mcc_novel` — MCC которого клиент НИКОГДА не использовал в 177M строках!
- `anom_mcc_familiarity` — log(кол-во транзакций клиента в этом MCC)
- `anom_amt_vs_mcc_typical` — сумма vs обычная сумма клиента В ЭТОМ MCC
- `anom_gap_zscore` — нетипичный gap между транзакциями
- `anom_daily_velocity` — кол-во транзакций за день vs обычное
- `anom_hourly_burst` — burst активности за час

## План v16+: Стратегии прорыва за 0.101

### Приоритет 1: Pretest Profiles + Drift (потенциал 0.11+)
**Суть**: Пересчитать customer profiles из 14M pretest строк (Jun-Aug'25).
Pretest = тот же период что test → distribution shift для profile-фичей исчезает.

**Drift фичи** (новые): сравнение pretrain vs pretest нормы клиента.
- `drift_amt = pretest_avg_amt / pretrain_avg_amt` — рост/падение трат
- `drift_mcc_change` — сменились ли любимые MCC
- `drift_hour_shift` — сместилось ли время активности
Если клиент "вырос" — крупные суммы для него нормальны, не аномалия.

**Реализация**: ~2-3 часа, средняя сложность.

### Приоритет 2: Z-score нормализация по месяцу (борьба с shift)
**Суть**: Вместо raw `cnt_24h = 10` → `cnt_24h_zscore = (10 - month_mean) / month_std`.
Убирает временной тренд из базовых фичей — модель видит отклонение от нормы месяца,
а не абсолютное значение (которое меняется от Oct'24 к Jun'25).

**Реализация**: ~1 час. Легко тестируется на val.

### Приоритет 3: Red vs Yellow score как фича
**Суть**: Маленький LGBM на 87K (fraud vs confirmed), его predict = доп. фича
в основную модель. Помогает отличить настоящий фрод от ложной тревоги.
НЕ labeled-only модель, а именно фича из вспомогательной модели.

**Реализация**: ~30 мин. Быстрый тест.

### Приоритет 4: Adversarial IPW (clipped)
**Суть**: Обучить классификатор train vs test, вес образца = p/(1-p) с clipping max=10.
Заставляет LGBM игнорировать фичи, специфичные для train-периода.

**Риск**: AUC=1.0 → extreme weights. Нужен жёсткий clipping.
**Реализация**: ~2 часа, средняя сложность.

### Приоритет 5: Focal Loss вместо binary cross-entropy
**Суть**: custom objective для LGBM, фокус на hard examples.
Уменьшает вклад легко классифицируемых green в градиент.
Модель больше учится на пограничных случаях (yellow-like green, quiet fraud).

**Реализация**: ~30 мин. Замена objective в LGBM params.

### Приоритет 6: Двухстадийный классификатор (Green vs Not-Green → Red vs Yellow)
**Суть**: Stage 1 = отсечь очевидную норму (green vs red+yellow).
Stage 2 = среди подозрительных отличить fraud от false alarm.
НЕ путать с v9 two-stage (susp×fraud multiplication) — тот провалился.
Здесь: вероятность Stage2 ЗАМЕНЯЕТ Stage1 для подозрительных, а не умножается.

**Риск**: v9 two-stage уже провалился на LB (-2%). Нужно другую архитектуру.
**Реализация**: ~2 часа.

**3. ✅ Двухстадийный Red vs Yellow — ПЕРЕОСМЫСЛЕНИЕ нашего провала v9**

ВЕРДИКТ: ⚠️ Мощно, но непрактично для наших ресурсов и дедлайна.

**6. ⚠️ Bagged Hill Climbing для ансамбля — ПОЛЕЗНО НА ФИНАЛЬНОМ ЭТАПЕ**

## v16: Pretest Profiles + Drift + Z-score + IPW (2026-03-17/18)

### Контекст
v14-C (LB=0.1010, val=0.044) — рекорд. 121 фича (91 base + 30 anomaly).
Цель v16: побить рекорд через борьбу с distribution shift (adversarial AUC=1.0).

### Pretest Deep Profiles
- Вычислены ПОЛНЫЕ deep profiles из pretest.parquet (14M строк, Jun-Aug'25)
- 96,953 клиента, 39 колонок (тот же формат что deep_customer_profiles)
- 91,058 клиентов с >=10 транзакциями (для hybrid)
- Кэш: features/pretest_deep_profiles.parquet, features/pretest_mcc_profiles.parquet

### Эксперимент v16-A: Hybrid Profiles (заменяем old → pretest)
- **Подход**: anomaly features считаются от PRETEST profiles (вместо pretrain+train 177M)
- Hybrid: pretest если >=10 tx, иначе fallback на old (91K + 9K)
- **Результат**: val=0.04558 (ensemble), **но крайне нестабильно**
- Seeds: 0.052, 0.034, 0.034, 0.047, 0.040 — iter от 547 до 9554!
- **Причина**: pretest profiles на train данных (Oct-May) = temporal mismatch

### Эксперимент v16-B: v14-C + 5 Pretest Anomaly Features (additive)
- **Подход**: НЕ заменяем old profiles, а ДОБАВЛЯЕМ 5 новых фичей из pretest
- pt_anom_amt_zscore, pt_anom_amt_vs_median, pt_anom_hour_zscore, pt_anom_mcc_novel, pt_anom_frequency
- **Результат**: val=0.053538 (+21.7% vs v14-C), **LB=0.0965 (-4.5%!)**
- Seeds стабильные: 0.051, 0.054, 0.053, 0.051, 0.051 — все 9.4K-10K iter
- **ВЫВОД**: val↑ → LB↓. Pretest фичи = утечка через клиентов, помогает на val но вредит на LB

### Эксперимент v16-C: v14-C + 3 Drift Features (additive)
- drift_amt_mean_ratio, drift_frequency_ratio, drift_hour_shift
- **Результат**: 1 seed done (val=0.053, iter=8980), процесс убит
- Не завершён, но val аналогичен B → скорее всего тоже хуже на LB

### Эксперимент v16-Z: Z-score нормализация velocity фичей по месяцу
- **Подход**: ЗАМЕНЯЕМ velocity фичи (cnt_*, amt_sum_*, secs_since_last) на z-score по месяцу
- Monthly stats вычислены из train, применены к train/val/test
- **Результат**: крайне нестабильно! Seeds: 0.051, 0.031, 0.051 (3/5 done)
- **Причина**: деревья не нуждаются в нормализации, z-score удаляет информацию
- **ВЫВОД**: z-score velocity = вредно для LGBM

### Эксперимент v16-IPW: Adversarial Importance-Weighted training
- **Подход**: обучить adversarial (train=0 vs test=1), использовать P(test|x) для весов
- Adversarial OOF AUC = 1.0 (идеальное разделение даже со слабой моделью)
- Top shift features: dormancy_days, cum_unique_mcc_approx, month, day_of_month
- P(test|train): mean=0.0015, max=0.53 — почти все train ~0, лишь единицы похожи на test
- Weights после IPW: mean=1.0, std=0.51, min=0.985, max=108 (clip5)
- **Результат**: в процессе (clip5: seeds 42=0.051, 123=0.044)

### Ключевые выводы v16
1. **Pretest profiles на val помогают (+22%), но на LB вредят (-4.5%)** — утечка через клиентов
2. **Z-score velocity = вредно** для деревьев (удаляет информацию, не нуждаются в нормализации)
3. **Adversarial IPW затруднён** при AUC=1.0: нет overlap → экстремальные/неинформативные веса
4. **Distribution shift ПЕРВАСИВЕН и НЕУСТРАНИМ** на уровне фичей — возможно нужен другой подход
5. **Правило "val↑ ≠ LB↑" подтверждено ещё раз** — pretest фичи = яркий пример

**НЕОЖИДАННЫЙ РЕЗУЛЬТАТ**: clip20 практически равен рекорду!
- Больший clip → лучше LB (обратная тенденция к val)
- clip10: val +14.7% → LB -2.9%
- clip20: val +16.0% → LB -0.1%
- Тренд: clip↑ → LB↑ (при этом val меняется слабо)

**ГИПОТЕЗА**: IPW с высоким clip агрессивнее перевешивает к test-подобным примерам.
При AUC=1.0 это значит: единичные train примеры, случайно похожие на test, получают
вес до 108×. С clip=20 максимальный вес ограничен 20×, с clip=10 — 10×.
Парадокс: большая дисперсия весов (clip20) даёт лучший LB.

**ИТОГ IPW**: параболическая зависимость clip→LB. Clip20 = оптимум.
- Слишком низкий clip (10): недостаточно перевешивает к test-подобным примерам
- Оптимальный clip (20): баланс между shift-коррекцией и шумом весов
- Слишком высокий clip (50, 100): единичные "test-подобные" примеры с весом 100× = шум
- clip50 и clip100 фактически эквивалентны (реальный max weight = 103, оба не клипают)

IPW не способен побить рекорд при adversarial AUC=1.0. Стратегия исчерпана.
